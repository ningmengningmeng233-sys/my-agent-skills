# ADR-0003: 全局资产登记表与并行候选+分层聚合

- 状态: Accepted
- 日期: 2026-08-16

## 背景

段级提取（v2）每段独立直调、段间零重叠、无全局上下文注入，导致：

1. **跨段命名漂移**：段 A 建"音响"、段 B 建"加强混音器"，聚合层只能靠摘句重叠猜测是否同实异名；
2. **跨段漏提**：前段建档、后段只写"他/那台机器"，后段模型无全局视野，识别不出已有资产；
3. **主名规则悬空**：CONTEXT.md 定义"主名取全局首次出现/最频繁称呼"，但现状没有任何全局机制，只能靠聚合层事后猜。

用户诉求"通读全文、保证不出差"，且明确要求不牺牲速度。

## 决策

新增全局登记表层，位于段级提取之前，共两遍：

1. **候选遍（并行）**：每段一次独立直调，只输出本段「候选主名表」（主名/别名/首现章/一句定性，每段约 10~20 条），不细提取。所有段并行。
2. **分层聚合遍（并行轮次）**：候选表两两合并，每轮模型裁决"两个候选是否同一资产、主名取哪个（原文首次/最频繁称呼，遵循主名规则）、别名并入"，轮数 ≈ log₂(段数)，每轮内部可并行。

产出「全局资产登记表」：每个资产一行（主名/别名/首现章/一句定性）。段级提取时注入登记表作锚点：登记表已有资产必须用主名，疑似新资产须标 [新增] 并附出处。

## 权衡

| 备选 | 优点 | 缺点 |
|---|---|---|
| 串行滚动锚点（第 N 段携带前 N-1 段登记表） | 每段都有前文共识，一致性最"平滑" | **串行**，100 段 = 100 次串行调用，与提速诉求冲突 |
| **并行候选 + 分层聚合（选定）** | 所有直调并行，耗时 ≈ 提取遍一次的量级；合并裁决时模型同时可见两张候选表的完整条目（含摘句），比提取遍盲猜可靠 | 合并裁决需要模型二次判断，存在合并错误风险（由聚合对账层兜底） |

## 影响

- 新增 `scripts/scan_registry.py` + 候选遍模板 + 聚合遍模板
- 改造 `extract_segments.py` + `段级提取模板.md`（注入登记表锚点、[新增] 申报）
- 改造 `aggregate.py`（登记表 ↔ 段记录对账）
- token 成本增量 ≈ 候选表输出（每段 0.5~1k）+ 分层合并输出 ≈ 全局扫描一遍的量级
