## 2. 性能基准：目标、实测与分解证据

夹具：`测试/fixtures/asset_compiler_regression`（脱敏源文本，17 项正式资产）。
两链**同夹具、同前半段**（拆分/登记/提取/聚合），差异只在尾段：
旧链路逐资产发模型调用生成提示词；新链路由总账确定性编译。

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 文本调用下降 | ≥ 0.60 | **0.6296**（旧 27 次 → 新 10 次） | 达标 |
| 文本墙钟下降 | ≥ 0.50 | **0.5809** | 达标 |
| 无关任务重跑下降 | ≥ 0.80 | **1.0**（旧：改一个资产要重算全部；新：0 次模型调用） | 达标 |
| 质量六项（事实覆盖/证据完整/关系合法/风格冲突/提示词完整/审核契约） | 不低于基线 | 6/6 不劣于基线 | 达标 |

**墙钟判定用「实测模型」而不是端到端秒表，理由是可复现**：
`wall_model = 本地实测开销（0 延迟墙钟的最小值） + 调用次数 × 端点延迟`。
三个输入全部来自实测，公式唯一；端到端实测值**并列写在报告里供对照**
（本机实测过旧链从 2100 ms 尖峰到 4110 ms 的负载抖动，足以把比值压到目标线下——那与代码快慢无关）。

**延迟扫描**（本地 mock 端点是瞬时的，不注入延迟就测不出「少调用 17 次」的意义；
两链同一延迟重复实测，`--delay-sweep` 可复跑）：

| 端点每次调用延迟 | 旧链路墙钟 | 新链路墙钟 | 下降 |
|---|---|---|---|
| 0 ms（本地开销下限） | 2094 ms | 2193 ms | 本地净开销基本持平（新链多一次总账+编译，少 17 次调用） |
| 300 ms | 10132 ms | 5128 ms | 0.4939 |
| 1000 ms（判定所依据的保守下限） | 29053 ms | 12146 ms | 0.5819（模型值 0.5809） |

交叉点在 300–1000 ms 之间：真实模型端点对长提示词每次调用普遍在 1–10 秒，
因此 1000 ms 是**保守**取值，不是挑出来的好看数字。

**质量指标的取样面在报告里明写**（`quality_basis`），避免被读成同口径提升：
`fact_coverage` / `prompt_complete` / `relations_valid` / `review_contract` 两链同口径；
`style_conflicts` 与 `evidence_complete` 旧链路取正式提示词节、新链路取编译产物——
实测 `style_conflicts` 17 → 0、`evidence_complete` 0.0 → 1.0。

**逐项计数（工单 14 步骤 4）**：旧 17 资产 / 17 提示词节，新 17 资产 / 17 提示词节，**逐项相等**；
图片任务两链均未创建视觉计划，记 `NOT_RUN`——**不报 0 冒充相等**。

## 3. 签发契约（v2.17 起为 9 项）

| 检查 | 判什么 | 缺测时的行为 |
|---|---|---|
| `check_schedule` / `check_final` / `check_asset_index` | 既有三张表与索引完整性 | 保持原样 |
| `check_asset_coverage` | 数量守恒：正式资产 = 已产提示词 + 明确待审 + 明确阻断 | 无总账也无索引时判「不适用」 |
| `check_art_constitution` | 项目美术总则内容指纹自洽 | 文件缺失＝未设定（放行），指纹不符＝失败 |
| `check_artifact_graph` | 有总账就必须有依赖图，边不悬空，必需提示词节点齐备 | 无总账时判「不适用」 |
| `check_required_prompts` | 基础提示词覆盖 + 调度清单衍生节逐行对应 | 无索引时判「不适用」 |
| `check_visual_review` | **仅当产品结果含生图**（`direct_generate`）时参与 | 其余模式判「不适用」并放行（两线独立） |
| `check_package_files` | 包内必备文件在盘；清单**仍自洽**时核对登记产物 | 旧签发已被新变化取代时不判死（否则追更后永远无法重签） |

**兼容影响（已在 CHANGELOG 写明）**：v2.16 及更早签发的 `交付清单.json` 缺 6 个新检查项，
`status` 会显示为待验证而不是已交付，重跑一次 `maintenance.py verify` 即可重新签发；
上一份清单自动复制到 `<资产库>/交付清单历史/` 留档。

## 4. 修掉的缺陷（本轮实测暴露，不是设计猜测）

1. **半截编译态**：`aggregate.py` 原先只写总账、不写依赖图，导致任何正常跑完管线的库都停在
   「有总账、无依赖图」，被新的 `check_artifact_graph` 判死。已改为产出侧成对落盘。
2. **追更死锁**：`check_package_files` 原先把「旧签发已过期」当失败，追加一章后旧清单必然过期，
   于是永远无法重新签发。已改为：时效性归 `status`，本项只管清单仍自洽时的包内文件。
3. **历史报告含机器绝对路径**：`docs/验收/v2.16.0-rc.1交付报告.md` 含 3 处绝对桌面路径。
   此前它因「当前版本报告不进包」的排除规则从未被打包，版本一升就暴露并中止打包。
   已把路径改写为占位形式（哈希、计数、结论一字未动，报告顶部有说明）。
4. **性能门形同虚设**：基准里 `--allow-not-run` 让「没接线」也能通过总门。新链路已接线，
   该开关已从总门撤掉，未测项现在会拦下晋级。
