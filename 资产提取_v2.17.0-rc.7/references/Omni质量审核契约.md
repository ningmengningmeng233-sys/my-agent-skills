# Omni 质量审核契约（按需加载）

> 判定图片是否合格时读本文件。硬规则与路由见 `SKILL.md`；
> 构图与站位的具体审法见 `references/导演构图与站位契约.md`。

## 一、谁有权判定

- **生成器永远没有签发权**：Gemini（含 Codex 转接）与任何外部工具只生成图片。
- **最终判定由当前运行的主模型给出**；用户开启审核子代理时，子代理只补充证据，不判定
  （见 `references/审核子代理-美术.md`、`references/审核子代理-技术.md`）。
- 程序不假设自己能直接调用对话中的主模型：审核走**文件往返**——
  导出 `review-request.json` → 主模型读图后写 `review-result.json` → 导入时校验绑定。

## 二、四种判定（用户可见中文）

| 判定 | 中文 | 后果 |
|---|---|---|
| `ACCEPTED` | 通过 | 允许发布为正式版本 |
| `PASS_WITH_NOTES` | 通过但有备注 | 允许发布，备注进入正式清单 |
| `NEEDS_REVISION` | 需要返工 | 禁止发布，进入返工或重做 |
| `NEEDS_HUMAN_DECISION` | 无法判断／需要人工决定 | 暂停该项，交主模型或用户 |

`QC_UNTRUSTWORTHY` 不是画作结论，而是「这次检查本身不可信」（缺证据、错任务、哈希对不上），
一律按不可信处理，不得当成通过。

## 三、问题码全集（34 个，其中 16 个是硬门）

**16 个硬门码**（存在任一即**不得**「通过」或「通过但有备注」）：
`HAND_FINGER_DEFECT`、`BODY_PROPORTION_DEFECT`、`IDENTITY_DRIFT`、`STYLE_MISMATCH`、
`CROP_MISMATCH`、`POSITION_MISMATCH`、`VIEWPOINT_MISMATCH`、`EYELINE_MISMATCH`、
`AXIS_CROSSING`、`OCCLUSION_MISMATCH`、`PROP_COUNT_MISMATCH`、`PROP_STATE_MISMATCH`、
`SCENE_STRUCTURE_MISMATCH`、`EXTRA_SUBJECT`、`TEXT_OR_WATERMARK`、`REFERENCE_CHAIN_INVALID`。

- 硬门码的严重度由**码本身**决定：检查器把它标成 minor 也会被强制为阻断级。
- 同义旧码按 `CODE_ALIASES` 归一到硬门码（如 `BODY_PROPORTION_ERROR`→`BODY_PROPORTION_DEFECT`、
  `SUBJECT_CROPPED`→`CROP_MISMATCH`、`SPACE_*`→`SCENE_STRUCTURE_MISMATCH`），**不得**用旧码绕过新硬门。
- 其余问题码（画风细节、材质、服装完整、发型结构、空间锚点、道具轮廓等）按严重度分级；
  非硬门的小问题仍可「通过但有备注」。

## 四、逐项检查清单（`templates/视觉质检/`）

- 人物：**对每只可见手逐项检查**（手指数、分离、关节、抓握、遮挡合理性）、比例、身份、服装、发型、
  拼版禁令、文字水印，以及**站位与机位语义**（左中右、前中后、距离、朝向、视线、轴线、遮挡）。
- 场景：锚点、空间关系、事实边界、连接、材质、人物禁入、裁切、拼版、文字水印、结构硬门、机位。
- 道具：轮廓可读、材质、形制比例、状态、数量、裁切、遮挡、人物禁入、拼版、文字水印。
- 三份清单都把**全部 16 个硬门码**列为阻断（硬门是全局口径，不按资产类型裁剪）。

**审核容差**：关系正确即可，**不要求像素级坐标一致**；人物在指定区域内小幅变化不算缺陷。

## 五、审核绑定（六项哈希）

审核请求与结果必须绑定并一致：任务编号、图片 SHA-256、提示词哈希、参考图集合哈希、画风包哈希、
构图卡哈希。任一项变化，审核立即失效——旧结果不能用于新输入，也不能用于后续轮次。

- 请求路径：`视觉资产/审核请求/<任务ID>/review-request.json`
- 结果路径：同目录 `review-result.json`
- 子代理草稿：同目录 `subagent-merge.json`（只含证据、不含判定，`requires_main_model = true`）
- 逐项清单缺项、问题码未知、缺证据或缺修复指令、密钥样式字段——一律不可信。

## 六、发布前置条件

判定 ∈ `ACCEPTED` / `PASS_WITH_NOTES`；六项绑定对**当前输入**仍成立；图片可读且 MIME/尺寸合规；
上游依赖都已在 `视觉资产/正式版本.json` 里有 `current`；
并且**只有发布器**能写正式版本清单——直接拷贝、改 Markdown、改状态字段都不算数。
## 七、看图顺序（六步）

> 同一张图，按下面这个**固定顺序**过一遍，再对照 §三 的问题码全集写结论。
> 顺序本身不改变判定权、不增删问题码（仍是 34 个，其中 16 个硬门），
> 也不改动 §五 的六项哈希绑定——它只规定「先看什么、后看什么」，
> 避免先入为主把硬门漏在过去。

1. **技术完整性**：图能否正常打开；尺寸、比例、长宽是否符合该任务规格；不是半张、不是糊图、不是纯色块。
2. **主体 / 身份与参考用途**：画面主体是谁、这份产物用在哪个用途（正脸 / 后脑 / 服装独立正面 / 服装独立背面 / 全身正面 / 全身背面）；主体是否唯一；身份与参考图（源头脸）是否一致。
3. **解剖 / 物理与接触逻辑**：手指数量与关节、身体比例、道具抓握方式、脚与地面的接触、布料与身体的贴合是否成立（对每只可见手逐项过）。
4. **Prompt 与任务符合度**：画面是否符合该任务的提示词与参考图要求——服装件数与配饰、发型、道具状态、视图规格（三格图板 / 三视图 / 单画面）是否与要求一一对应。
5. **构图与可读性**：站位（左中右）、机位（前中后）、距离、朝向、视线、轴线、遮挡是否与构图卡一致；主体是否清晰可读；背景与留白是否合规。
6. **通用生成伪影**：文字与水印、多格拼版、边缘裁切（裁头顶 / 裁脚）、重复肢体、材质崩坏等通用伪影。

六步顺序是**看图的方法**，不是判定的替代：任一步命中硬门码即阻断（`不得「通过」或「通过但有备注」`）；前面的步骤没问题，不构成后面步骤可以放行的理由。
