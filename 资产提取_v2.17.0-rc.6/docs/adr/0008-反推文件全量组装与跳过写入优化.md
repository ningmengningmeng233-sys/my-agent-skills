# ADR-0008: 反推文件全量组装与跳过写入优化

- 状态: Accepted
- 日期: 2026-08-18

## 背景

`aggregate.py` 每次运行都会调用 `render_final()` 重新生成 `反推_最终.md`，即使只修正了单个裁决块。虽然组装过程不涉及 LLM 调用，但对于超长篇项目，文件写入与解析仍需数秒；追更场景下所有块产物均未变化时，也会触发无意义的重建。

## 决策

保持「最终文件始终从全部块产物全量组装」的策略，并增加 **hash 一致时跳过写入** 的优化：

1. 组装前收集本次参与组装的各块产物 hash（`裁决_<块>.md` 与 `裁决输入_<块>.md`）。
2. 与上一次最终文件生成时记录的 hash 集合比较。
3. 若所有 hash 完全一致且 `反推_最终.md` 已存在，则跳过写入，直接复用现有文件。
4. 只要任一输入块发生变化，就执行全量组装并更新记录的 hash 集合。

## 权衡

| 备选 | 优点 | 缺点 |
|---|---|---|
| A. 块级增量更新最终文件 | 写入量最小 | 实现复杂，块与块之间的待确认附录、合并统计需跨块一致，易引入不同步 |
| B. 保持全量重建 | 逻辑简单、一致性绝对保证 | 无变化时也重建，浪费少量 I/O |
| C. 全量组装 + hash 跳过（选定） | 兼顾一致性与效率 | 需要额外记录 hash，首次生成后生效 |

选择 C 是因为最终文件是多个块产物的汇总，任何跨块信息（如合并统计、待确认附录）都必须在同一次组装中保持一致；块级增量更新风险高于收益。

## 影响

- 修改 `scripts/aggregate.py`：组装前读取/写入块产物 hash 快照。
- hash 快照可存放在 `反推_最终.md.hash` 或 `.asset_state.db` 中；为减少对 SQLite 模式的依赖，推荐与现有 `.hash` 文件机制保持一致。
- 追更时若无新增块或块产物未变，`aggregate.py` 调用将快速返回，不重建最终文件。
