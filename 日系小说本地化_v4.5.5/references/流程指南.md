**完成标准（六件套验收完整规则、证据句三验与返工条款以本节为单源真相；
SKILL.md「批稿路径的交付字段」只登记脚本机械判定的两个字段名，不重复展开细则）**：
六件套（①整批完整 ②篇幅守恒 80%-120% ③硬门槛全过
④风格对照证据句≥3 ⑤爽点对照证据句逐条 ⑥情节保真）+ 独立盲审，双通过才标"已完成"，
否则标"待返工"；同一批返工 3 次仍不过 → 升级"待人工处理"。
**盲审硬约束**：`状态: 已完成` 当且仅当 ①六件套全过 ②盲审结论已写入且非
"待盲审"——缺一即"待返工"；断点库 mark_done 只在盲审结论存在后调用。
**红线硬约束**：红线记录无 `确认来源`（用户拍板记录）= 红线未确认 =
该批不得标"已完成"；AI 无权宣布"已确认"。

## 七、风格锚点（全书开工时定标一次）

### 位置：阶段二点五（拆批预处理完成后、阶段三改写开始前——对应 SKILL.md Step 2 确认与 Step 3 单章改写之间）——拆批完成后才能抽章定标

### 流程（一次定标）

```
1. 拆批完成后，从全书随机抽 1-2 个典型推进章（有冲突/打脸/对话的章节，不选铺垫章）
2. AI 按全部规则改写锚点章（同步走全库参考协议：全库检索 → 构建参考池 → 精读 → 列清单 → 证据句）
3. AI 输出《风格指标报告》：对话+动作占比/氛围段占比/金句数/打脸围观化/章末钩子/篇幅变化率/情绪外放 + **爽点清单**（本场景应具备的爽点）
4. 用户审读锚点章 + 指标报告，逐项拍板（"对话太少→调""金句不够→补"）
5. 完成标准（两项都满足才算定稿）：
   a. 7 项指标全部落入目标区间（上表）
   b. 用户对锚点章明确说"可以/通过/OK"
   任一未满足 → 回到步骤 3 修改循环
6. 定稿 → 生成《风格锚点.md》（锚点章原文 + 指标区间 + 风格描述 + 爽点对照——
   风格+爽点双基准）
7. 后续每批改写，AI 对照《风格锚点.md》校准
```

### 指标区间（初版）

| 维度 | 指标 | 目标区间 |
|------|------|---------|
| 对话+动作占比 | 可脚本统计 | ≥70% |
| 氛围段占比 | 段落分类统计 | ≤20% |
| 金句数 | 人工/AI 识别 | 每章 ≥1 句 |
| 打脸围观化 | 检查人物反应 | 有冲突场景必有 |
| 章末钩子强度 | 人工判断 | 有强悬念 |
| 篇幅变化率 | 改写后/原文 | 80%~120% |
| 情绪外放程度 | 人工判断 | 比原文外放一档 |

### 漂移检测（每 10 批一次）

- AI 随机抽 1 段本批文本 vs 锚点章同类型段落，自查风格是否漂移
- 检测到漂移 → 回看《风格锚点.md》重校，需要时请用户确认修正方向
- 抽检本身轻量（AI 自查），只在漂移确认时才需用户参与

### 锚点中途变更（用户调风格方向）

- 变更只影响**后续批次**；已完成批**不自动返工**
- 每 10 批待确认清单提示"风格已变更，是否重写已完成 X 批？"，
  用户指定才返工（走局部返工流程）

## 八、盲测方案（每卷一次）

1. 该卷随机抽 2-3 段改写后文本
2. 混入 1 段正常中国网文（对照）
3. 找 3 人（用户 + 1-2 个不熟日漫的朋友）判断"哪段是翻译的"
4. 错判率 ≥ 2/3 才通过；否则该卷返工
5. 结果记入质检报告

## 九、调度策略（决策：改写串行，预处理并行）

```
全书
 ├→ [并行 32路] 拆批（split_ja_segments.py）
 ├→ [并行 32路] 段落分类预处理（混合文体规则）
 └→ [串行] 逐批改写（每批：查表→改写→更新表→硬门槛→写进度）
       └→ [并行 32路] 批质检（硬门槛扫描）
全书完成
 └→ 终审扫描 + 独立盲审 skill 打分 + 用户抽读
```

**为何改写串行**：映射表逐批更新是全局状态，并行会导致跨批冲突；
预处理（拆批/分类/质检）不依赖映射表，可并行加速。

## 十、进度管理（断点续跑）

1. 每批完成后写断点库：`批次号 | 状态 | 映射表版本 | hash`
   **调用序列（顺序不能错）**：开始前 `mark_pending(批路径, 输出路径)` → 完成后
   `mark_done(...)`（mark_done 是 UPDATE，未先 pending 会静默失败 → 断点无效）；
   失败 `mark_failed(批路径, 原因)`；`should_skip(批路径, 输出路径)` 判断跳过
   （输出缺失/源文件 hash 变化 → 重跑）
2. 断线/中断 → 重读断点库 → 从未完成批继续，已完成的跳过（零浪费）
3. 映射表更新 → 受影响批次 hash 失效 → 自动重跑（防行号漂移/译词漂移）
4. git 版本管理（可选）：映射表每 10 批提交一次，可回滚任意批次

### 断点恢复步骤（明确流程）

```
1. 读 .index_state.db（断点库，07_缓存/ 或索引库根，由调用参数决定），
   列出全部批次状态（待处理/改写中/质检中/已完成）
2. 定位状态为"改写中/质检中"的批次 → 视为中断，回退为"待处理"重新执行
   （hash 检测保证：已完成的批不变更则不重跑）
3. 从第一个"待处理"批继续，按章节顺序推进
4. 恢复后向用户汇报：已完成 X 批 / 剩余 Y 批 / 本次恢复点
```

**完成标准**：.index_state.db 中所有批次状态 = "已完成"，且无"待人工处理"标记，
才视为全书改写完成。

## 十一、待确认清单机制（每 10 批）

输出清单，含四类待确认项（顺带刷新 `08_索引库名单\书目清单.md`）：

```
【待确认清单 #3】（批次 21-30）· 进度: 已完成 30/200 批（15%），剩余约 17 轮
├─ 红线遗留（3项）:   ← 仅未当场拍板的项
│   1. 第24章 未成年恋爱桥段 → 建议 A保留/B调整/C删除
│   2. ...
├─ 映射冲突（2项）:
│   1. 「式神」在21批译为"符灵"、28批译为"役灵" → 统一为?
│   2. ...
├─ P2 低置信抽查（5项）:
│   1. 「拉面」→"汤面"（第23批）→ 确认/改?
└─ 回填通用词库候选（≥5条新词时）:
    1. 「便利店」→"小卖部" 等
└─ 风格变更提示（锚点变更后）:
    "风格已变更，是否重写已完成 X 批？"（用户指定才返工）
```

用户批量拍板后，写回映射表并解除锁定。
