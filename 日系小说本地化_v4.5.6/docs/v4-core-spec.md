# 日系小说本地化 v4 Core 规格

> 状态：提案设计
> 适用范围：v4 Core
> 不适用：v3 既有脚本、旧工作区自动迁移、参考池/文风卡/平台专项审查等增强功能

## 1. 目标与非目标

### 1.1 目标

v4 Core 接受已经是中文的日系小说稿，输出可阅读的中国化中文小说成品，并且能够证明：

- 输入章节与输出章节一一对应；
- 原作事件图、因果链、人物目标、关系变化、情感结果和世界观功能未被普通本地化改写改变；
- 核心译名和高风险处理经过用户决策；
- 未决、失败、返工或带风险的章节不会混入正式成品；
- 任一章节可以独立重跑，旧正文不会冒充新决策结果；
- 所有状态、决策、检查和合并结果可追溯。

### 1.2 非目标

v4 Core 不负责：

- 从日文原稿翻译成中文；
- 自动创作新剧情、补写剧情或改变原作事件；
- 自动替用户处理审核红线；
- 保证“完全看不出原作来源”；
- 机械证明文风、爽点、AI 味、情绪强度或读者观感；
- 依赖索引库、参考池、文风卡、示范库才能运行；
- 执行红果、番茄等平台专项审核；
- 自动把 v3 工作区解释或迁移为 v4 工作区。

## 2. 产品边界

### 2.1 输入

输入必须是中文小说稿，支持简体或繁体。输入可以是单文件或章节文件夹，但必须通过章节边界预检。日文原稿、非小说文本和无法确认边界的材料进入阻塞状态，不得静默改写。

原始输入先归一化为只读快照：单文件复制为 `source/original.<ext>`；章节文件夹按确定的文件顺序复制到 `source/files/<file-id>.<ext>`，并生成清单记录相对路径、顺序、编码和哈希。`manifest.source.boundary_status` 只表示项目级边界摘要；每章 manifest 状态是章节边界的权威记录。只要任一章节仍待确认，项目不能声称边界已全部确认。后续所有检查和改写都以快照为准，不直接读取用户可能继续变化的源文件。

### 2.2 普通本地化边界

普通本地化只改变：

- 表达方式；
- 人名、地名、称谓和文化外壳；
- 语域、句式和叙事节奏；
- 不改变剧情功能的场景呈现方式。

普通本地化不得默认新增、删除、合并、拆分或调换剧情事件，不得改变事件因果、人物目标、关系变化、情感结果或世界观功能。

### 2.3 剧情级变更

以下任何行为都属于剧情级变更，不属于普通本地化：

- 新增、删除、合并、拆分或调换事件；
- 改变事件因果或事件结果；
- 改变人物目标、关系变化或情感结果；
- 改变世界观功能；
- 为审核而改变上述内容。

剧情级变更必须进入决策文件，取得用户批准，重新生成受影响事件图和正文，并重新执行全部硬门槛。

## 3. 三级本地化策略

| 类别 | 默认处理 | 例子 |
|---|---|---|
| 必须替换 | 自动处理并记录；核心词仍须用户确认 | 人名、称谓、地名、现实日本机构、现实日本生活方式、日式出版注释、台版翻译腔 |
| 按剧情功能适配 | 先标记功能，再提出处理；可能进入 C 档 | 神社、祭典、剑道、阴阳师、式神等承担剧情或世界观功能的元素 |
| 默认不得替换 | 保留原功能和设定；用户另行要求才变更 | 魔法、骑士、精灵、异世界力量体系及其他非日本来源的西幻/架空设定 |

“全面中国化”在 v4 中不再等于清除所有日本痕迹，而是替换现实日本外壳，同时保护事件图和世界观功能。

## 4. 交互分层

### A 档：必须用户确认

- 书名；
- 主角和核心角色译名；
- 核心组织、地点和固定设定；
- 改变事件图、人物目标、关系或结果的处理；
- 审核处理的保留、调整或删除；
- 源稿确定矛盾或疑似矛盾的处理；
- 用户明确指定的风格方向。

### B 档：默认自动处理但可追溯

- 低风险日常词；
- 常规台翻腔和普通中文母语化；
- 标点和格式；
- 不改变功能的生活文化替换。

系统必须记录原词、结果和规则版本，但不把每次自动替换伪装成用户决策。

### C 档：冲突升级

以下情况进入 C 档，未决时阻塞相关章节：

- 低置信度译名；
- 同一原词出现多个项目级译名；
- 可能改变世界观功能的文化元素；
- 可能改变人物声线的称谓；
- 检测器无法判断的事实矛盾；
- 平台风险边界不明确的内容。

## 5. Core 工作区契约

```text
<工作区>/
├── source/
│   └── original.<ext>                 # 用户输入归一化后的只读快照
├── chapters/
│   └── <chapter-id>/
│       ├── source.md                   # 单章节原文快照
│       ├── events.json                 # 事件图初稿/确认版
│       ├── decisions.json              # 章节级用户决策
│       ├── output.md                   # 纯章节标题+正文
│       ├── checks.json                 # 硬门槛、事件对照、软评估
│       └── audit.jsonl                 # 章节追加式审计
├── project-decisions.json              # 项目级用户决策
├── manifest.json                       # 唯一当前状态真相
├── audit.jsonl                         # 项目追加式审计
└── output/
    └── localized.md                    # 只合并已通过章节
```

### 5.1 文件职责

| 文件 | 权威内容 | 是否可由用户编辑 |
|---|---|---|
| `source/original.*` 或 `source/files/*` | 原始输入归一化快照 | 否；如需变更必须创建新项目版本 |
| `chapters/<id>/source.md` | 该章节原文快照 | 否；由系统从输入快照生成 |
| `events.json` | 事件图及高风险节点确认状态 | 系统生成，用户通过决策文件确认 |
| `project-decisions.json` | 全书级用户决策和项目级映射 | 是；系统验证后生效 |
| `decisions.json` | 单章上下文决策、矛盾处理和审核决策 | 是；系统验证后生效 |
| `output.md` | 可交付章节正文 | 不作为审批入口；人工修改会触发哈希失效 |
| `checks.json` | 检查结果和事件级对照 | 系统生成，不手改结果 |
| `manifest.json` | 每章唯一当前状态、指纹和交付资格 | 用户可查看，不得直接改状态 |
| `audit.jsonl` | 追加式运行、决策和状态历史 | 只追加，不修改历史 |

`experimental_output` 只在用户坚持带风险生成时出现，必须与风险原因和独立输出路径一同登记；它永远不参与正式合并。风险版的路径和原因记录在章节 manifest 字段中，不能只写在报告或日志里。

正文文件不得包含写前计划、爽点清单、质检结果、映射说明、状态、审批或审计元数据。

### 5.2 原子写入与并发

- `manifest.json` 必须通过临时文件写入后原子替换；
- 状态更新必须持有项目锁，禁止两个进程同时覆盖同一个 manifest；
- `audit.jsonl` 每次追加一条完整 JSON 记录，失败不得写半行；
- 任何写入失败都保留旧 manifest，不得产生半更新状态；
- 合并前必须重新校验 schema、指纹和所有入选章节。

## 6. 单章节工作项

单章节工作项是 v4 的最小可信单位。批次只能用于调度、资源分配或并发控制，不拥有事实或通过状态。

每个工作项至少保存：

1. 原文快照；
2. 事件图；
3. 项目级和章节级决策的有效视图；
4. 纯正文；
5. 硬门槛和事件级对照；
6. 当前 manifest 状态；
7. 章节级审计日志。

超长章节可以内部技术分段，但分段不创建独立事件图、质检状态或交付状态。

## 7. 输入切分与源稿预检

### 7.1 章节边界

- 可识别的“第 X 章/话/回、序章、终章、番外”等标题优先；
- 文件夹输入按文件名排序读取，但仍需识别文件内章节边界；
- 无可靠标题时只生成候选章节边界，要求用户确认；
- 无法可靠切分时阻塞输入预检；
- 不得把任意字数块静默命名为章节。

### 7.2 源稿预检

每个章节改写前必须检查：

- 时间和顺序；
- 数字、数量和单位；
- 人物身份与称谓；
- 地点和空间关系；
- 事件前置条件、动作和结果；
- 元文本边界；
- 章节是否缺少前情或结尾。

检测结果分为：

- **确定矛盾**：证据足以证明同一事实冲突，阻塞章节；
- **疑似矛盾**：上下文不足，必须保留“疑似、待人工核”标记；
- **可解释差异**：记录解释依据后不阻塞。

“第二天”和“四天”这类序数与数量必须区分；检测器不能把启发式疑似直接写成确定错误。

确定矛盾或疑似矛盾必须通过 `decisions.json` 记录用户选择：保留、修正、标记为有意设定或暂停。决定生效后才可继续该章节。

## 8. 事件图

### 8.1 事件图初稿

AI 根据原文生成事件图初稿，每个事件至少包含：

- 唯一 `event_id`；
- 章节内顺序；
- 参与者；
- 前置事件；
- 动作；
- 结果；
- 主要人物目标；
- 关系变化；
- 世界观功能；
- 置信度和风险标签。

机械检查必须确认：

- ID 唯一；
- 顺序连续或可排序；
- 参与者、动作和结果非空；
- 前置事件引用存在；
- 高风险标签有原因。

### 8.2 高风险节点确认

事件图必须通过独立的 `events.json` 契约校验；事件级对照和软评估必须通过 `checks.json` 契约校验；章节决策和项目级决策必须分别通过 `decisions.json` 与 `project-decisions.json` 契约校验。Core 实现至少需要提供这些契约的 schema 或等价结构校验器，不能只校验 manifest 外壳。

以下事件必须由用户确认，或由已验证的决策文件明确处理：

- 因果链节点；
- 人物目标或关系变化；
- 剧情级变更候选；
- 源稿矛盾关联事件；
- 低置信度事件；
- 文化功能适配可能改变事件意义的节点。

普通、明确且无冲突的事件由 AI 初稿和机械结构检查覆盖，不逐条打扰用户。

## 9. 改写与事件级验收

### 9.1 改写要求

改写必须同时参考：

- 原文快照；
- 已确认事件图；
- 生效的项目级映射；
- 章节级决策；
- 三级本地化策略；
- 当前规则词典版本。

改写不得把计划、检查、参考资料或审计说明写入正文。

### 9.2 事件级对照

改写后必须在 `checks.json` 中为事件图的每个事件生成对照记录：

- `event_id`；
- 正文段落 ID；
- 参与者是否一致；
- 顺序是否一致；
- 结果是否一致；
- 因果是否一致；
- 文化功能是否保留；
- 是否发生剧情级变更；
- 证据和结论。

事件缺失、顺序或结果改变、文化功能丢失或证据无法定位时，章节不得通过。只有表达、命名、语域和文化外壳变化时，才可作为普通本地化通过。

段落 ID 由系统基于正文规范化分段和顺序生成，不写入展示正文；它只用于检查证据关联。行号不是 Core 的事实关联依据。

### 9.3 篇幅

正文与原文的篇幅比只用于异常提示：

- 过短：提示检查漏写；
- 过长：提示检查加戏或重复；
- 比例本身不能证明事实完整；
- 比例本身不能否决合法的中文化表达。

## 10. 质量模型

### 10.1 事实与交付硬门槛

Core 必须验证：

1. 输入快照存在且哈希稳定；
2. 章节边界已确认；
3. 事件图结构有效；
4. 高风险事件和 A/C 档决策已闭环；
5. 原文与正文一一对应；
6. 事件级对照全部有结论和证据；
7. 必须替换元素无未处理残留，或已有用户明确保留决策；
8. 正文格式、编码和章节顺序正确；
9. 输出、检查和决策指纹一致；
10. 工作项没有未决阻塞、返工、带风险或未经验证的手动覆盖；
11. manifest 状态与所有产物一致。

### 10.2 风格质量软评估

以下可以记录结果和证据，但不是 Core 的机械确定性承诺：

- 中国网文语感；
- 爽点质量；
- AI 味；
- 情绪强度；
- 叙述者声线；
- 读者是否识别出原作来源。

参考池、文风卡、示范库和独立盲审属于 Enhance；启用后必须记录是否使用及结果，但不得替代事实硬门槛。

## 11. 状态机

manifest 使用机器可读的 ASCII 状态值，中文含义如下：

| 状态 | 含义 | 可进入正式合并 |
|---|---|---|
| `new` | 已登记但尚未完成解析 | 否 |
| `awaiting_boundary` | 章节边界待用户确认 | 否 |
| `parsed` | 原文快照、章节边界和事件图初稿已生成 | 否 |
| `awaiting_decision` | 等待 A/C 档或矛盾处理决策 | 否 |
| `ready_for_rewrite` | 前置检查和必需决策已完成 | 否 |
| `rewriting` | 正在生成正文 | 否 |
| `awaiting_checks` | 正文已生成，等待硬门槛 | 否 |
| `rework` | 已确认存在错误，必须重新改写或修正 | 否 |
| `awaiting_review` | 已通过 Core，等待已启用的 Enhance 盲审 | 否 |
| `needs_review` | 指纹、文件、审计或检查结果不一致，待复核 | 否 |
| `passed` | 满足所有当前启用的通过条件 | 是 |
| `delivered` | 已被某次正式合并记录采纳 | 是 |
| `paused` | 用户暂停该章节 | 否 |
| `error` | 工具或运行错误，需人工恢复 | 否 |

核心迁移约束（分支和回环必须按下表实现，不得按线性文本拼接）：

| 当前状态 | 触发条件 | 下一状态 |
|---|---|---|
| `new` | 发现可靠章节边界 | `parsed` |
| `new` | 边界无法确认 | `awaiting_boundary` |
| `awaiting_boundary` | 用户确认候选边界 | `parsed` |
| `parsed` | 存在未决 A/C 决策或矛盾 | `awaiting_decision` |
| `parsed` | 无需用户决策 | `ready_for_rewrite` |
| `awaiting_decision` | 必需决策已验证 | `ready_for_rewrite` |
| `ready_for_rewrite` | 开始生成正文 | `rewriting` |
| `rewriting` | 正文生成成功 | `awaiting_checks` |
| `awaiting_checks` | 硬门槛失败或事件对照失败 | `rework` |
| `awaiting_checks` | 启用盲审且 Core 通过 | `awaiting_review` |
| `awaiting_checks` | 未启用盲审且 Core 通过 | `passed` |
| `rework` | 修正后重新生成 | `rewriting` |
| `awaiting_review` | 已启用盲审通过 | `passed` |
| `awaiting_review` | 已启用盲审失败 | `rework` |
| `passed` | 正式合并成功 | `delivered` |
| `passed`/`delivered` | 影响事实或表达的指纹变化 | `ready_for_rewrite` |
| 任意可恢复状态 | 用户暂停 | `paused` |
| `paused` | 用户恢复且输入仍有效 | 恢复到暂停前状态 |
| 任意运行状态 | 工具异常 | `error` |
| `error` | 人工确认错误已处理 | `needs_review` |
| `needs_review` | 指纹/文件/审计重新校验通过 | `ready_for_rewrite` 或暂停前安全状态 |
| `needs_review` | 校验仍失败 | `rework` 或继续 `needs_review` |

`awaiting_decision`、`needs_review`、`paused` 和 `error` 是章节状态；`blocked` 只表示检查结果语义，不是 manifest 状态。任意状态迁移都必须写入 audit，并由系统维护 manifest。

没有启用盲审时，`awaiting_checks` 通过后可直接进入 `passed`。任意影响事实或表达的输入指纹变化，都将 `passed`/`delivered` 回退为 `ready_for_rewrite` 或 `needs_review`。

### 11.1 结果语义

- `pass`：证据充分，硬门槛通过；
- `blocked`：无法安全判断或等待用户决策；
- `fail`：已确认错误，需要返工；
- `warning`：不阻塞但必须展示。

“不确定”只能是 `blocked`，不能写成 `pass`。`rework` 不是“已审查”，不能合并。用户坚持生成时，只能输出标记为实验/待人工的带风险版。

## 12. manifest 与权限

### 12.1 唯一状态真相

`manifest.json` 是项目级唯一当前状态真相。frontmatter、文件名、报告文字、旧 SQLite 状态和正文内容都不能单独决定章节是否可交付。

### 12.2 用户与系统权限

用户可以编辑：

- `project-decisions.json`；
- `chapters/<id>/decisions.json`。

系统负责：

- 校验决策结构、来源和哈希；
- 更新 manifest 状态和指纹；
- 写入 checks 和 audit；
- 生成或废止正文；
- 合并正式输出。

用户可以查看 manifest，但不得直接把状态改成 `passed` 或 `delivered`。若检测到手动修改或哈希不一致，自动进入 `needs_review`，禁止合并。

### 12.3 指纹失效

`project-decisions.json` 是 Core 的必需项目级决策文件；即使尚未有用户决策，也必须存在一个经过 schema 校验的空决策文件和初始 revision，不能省略顶层 manifest 引用。章节级 `decisions.json` 也必须在工作项创建时生成，至少包含空 entries 和初始 revision。

至少维护以下指纹：

- 原文快照；
- 事件图；
- 项目级决策；
- 章节级决策；
- 规则词典；
- 正文；
- checks；
- 工作项有效指纹。

影响事实或表达的变化必须使旧正文和后续检查失效。纯审计备注、报告排版、运行日志和无关章节变化不触发重跑。

## 13. 合并与交付

正式合并流程：

1. 原子读取并校验 manifest schema；
2. 重新计算每个候选章节的输入、正文和 checks 指纹；
3. 只选择 `state` 为 `passed` 或已在本次合并中合法记录的 `delivered` 章节；
4. 排除 `awaiting_boundary`、`awaiting_decision`、`rework`、`awaiting_review`、`needs_review`、`paused`、`error` 和带风险章节；`blocked` 只作为检查结果，不作为章节状态；
5. 按章节序号排序；
6. 验证章节数量、标题和顺序没有缺口；
7. 只拼接 `output.md` 的章节标题和正文；
8. 写入 `output/localized.md`，并把合并批次、manifest 指纹和章节 ID 写入审计日志；
9. 任一步失败都不覆盖旧正式输出。

最终正文不得包含：

- 写前计划；
- 爽点清单；
- 质检表；
- 映射说明；
- 状态或审批字段；
- 审计日志；
- 参考池或文风卡内容。

带风险版必须使用独立路径和明确名称，不能覆盖 `output/localized.md`。

## 14. Core、Enhance、Optional 分层

### v4 Core

- 输入快照和谨慎章节切分；
- 单章节工作项；
- 源稿预检和事件图；
- A/B/C 决策；
- 三级本地化；
- 事件级对照；
- 事实与交付硬门槛；
- manifest、审计和指纹失效；
- 正式合并。

### Enhance

Core 通过后再接入：

- 参考池；
- 文风卡；
- 示范库；
- 独立盲审；
- 读者盲测；
- 风格漂移检查。

Enhance 无法替代 Core 硬门槛；启用的盲审必须通过，否则章节不能进入 `passed`。

### Optional

最后再处理：

- 文风蒸馏；
- 平台专项审查；
- 发布拆章；
- 高级 AI 味检测；
- 多书并行；
- 复杂索引库轮换。

没有对应规则包时，不得声称完成平台专项审查或高级风格保证。

## 15. 迁移与版本策略

- v3.2.0 冻结为只读 legacy；
- v4 在独立版本和目录中并行建设；
- Core 用小型测试小说验证后，才考虑切换默认入口；
- 旧 v3 工作区不自动迁移；
- 迁移必须由显式工具或用户明确操作完成；
- v4 Core 完成前冻结 Enhance 和 Optional 的新增需求。

## 16. Beta 进入条件

必须同时满足：

1. `docs/v4-manifest-schema.json` 和 `docs/v4-artifact-schemas.json` 可被标准 JSON/schema 工具加载；
2. Core 契约测试全部通过；
3. 故意失败测试全部正确拦截或降级；
4. 小型测试小说人工验收通过；
5. 没有未解释的 P0 缺陷；
6. 正式输出只包含 manifest 判定的已通过章节；
7. 未使用增强层或平台规则包时，报告明确声明未使用。

测试矩阵见 `docs/v4-core-test-matrix.md`，manifest 契约见 `docs/v4-manifest-schema.json`。
