# v4 Core 测试矩阵

> 目的：证明 v4 Core 能正常完成可信路径，也能在危险或不确定输入下正确阻塞、返工或降级。
> 进入 beta 的门槛：契约测试全部通过、故意失败测试全部按预期拦截、小型测试小说人工验收通过、没有未解释的 P0 缺陷。

## 1. 测试结果语义

| 结果 | 含义 | 允许进入正式成品 |
|---|---|---|
| `pass` | 检查证据充分、条件满足 | 是，前提是 manifest 为 `passed` |
| `blocked` | 无法安全判断或等待用户决策 | 否 |
| `fail` | 已确认存在错误，需要返工 | 否 |
| `warning` | 非致命问题，必须报告 | 可以，但不能掩盖阻塞/失败 |

“不确定”必须得到 `blocked`，不得自动变成 `pass`。

## 2. 自动契约测试

### 2.1 工作区和 schema

| ID | 场景 | 预期 |
|---|---|---|
| C-001 | 创建最小 Core 工作区 | 生成 `source/`、`chapters/`、`manifest.json`、`audit.jsonl`、`output/` |
| C-001a | 创建空项目或边界未确认项目 | 允许 `chapters: []`，状态/边界字段明确表示未解析或待确认 |
| C-002 | 解析 v4 schema 契约 | `v4-manifest-schema.json` 和 `v4-artifact-schemas.json` 可加载；合法 manifest 和旁车文件通过 |
| C-002a | 空项目或边界未确认项目 | `chapters: []` 可通过基础 schema；项目级边界状态和后续章节状态决定是否可继续 |
| C-002b | 初始无用户决策 | 仍生成并校验空的 `project-decisions.json` 和各章 `decisions.json` 与 revision，不省略 manifest 引用 |
| C-003 | 缺少必填 manifest 字段 | schema 校验失败，不能继续合并 |
| C-004 | 章节 ID 重复 | 创建失败或 manifest 校验失败 |
| C-005 | 非法相对路径、`..`、Windows 保留字符 | schema/边界校验失败 |
| C-006 | 章节目录缺少 `events.json`/`checks.json`/`decisions.json` | 状态不得超过 `parsed` 或进入阻塞 |
| C-007 | `output.md` 含 frontmatter、计划或质检说明 | 正文纯度检查失败，不得通过 |

### 2.2 输入和章节边界

| ID | 场景 | 预期 |
|---|---|---|
| C-010 | 明确“第1章/序章/终章/番外”标题 | 正确创建章节 ID、标题和源范围 |
| C-011 | 章节文件夹按文件名排序 | 顺序稳定，来源路径可审计 |
| C-012 | 超长章节 | 只创建一个章节工作项，可生成内部技术分段；不产生独立交付状态 |
| C-013 | 无章节标题 | 生成候选边界，状态为 `awaiting_boundary`，等待用户确认 |
| C-014 | 无法可靠切分 | 阻塞输入预检，不静默按字数伪造章节 |
| C-015 | 输入快照生成 | `source/original.*` 或 `source/files/*` 和章节 `source.md` 哈希稳定；文件夹清单记录顺序、路径和哈希 |
| C-016 | 原始源文件在快照后被修改 | 工作项继续以快照为准；源文件变化被记录为新版本/待复核 |

### 2.3 事件图

| ID | 场景 | 预期 |
|---|---|---|
| C-020 | 普通明确事件 | 生成唯一 ID、顺序、参与者、动作、结果 |
| C-021 | 重复 event ID | 结构检查失败 |
| C-022 | 空参与者、动作或结果 | 结构检查失败 |
| C-023 | 前置事件引用不存在 | 结构检查失败 |
| C-024 | 高风险事件 | 标记风险原因并生成待确认项 |
| C-025 | 高风险事件决策已确认 | 解除对应阻塞，决策哈希进入指纹 |
| C-026 | 高风险事件未确认 | 状态保持 `awaiting_decision`，并在 blockers 或 checks 中记录 `blocked` 结果；`blocked` 不是 manifest 状态 |
| C-027 | 源稿数字/时间/人物矛盾 | 生成确定或疑似矛盾；未决前阻塞章节 |
| C-028 | “第二天/第四天” | 不得把序数“第二天”直接识别为数量矛盾；疑似项保留人工核标记 |

### 2.4 映射和决策

| ID | 场景 | 预期 |
|---|---|---|
| C-030 | 项目级核心译名确认 | 写入 `project-decisions.json`，受影响章节指纹更新 |
| C-031 | 章节级上下文决策 | 只影响该章节，不污染项目级映射 |
| C-032 | 规则词典版本变化 | 受影响正文指纹失效，状态回退 `ready_for_rewrite` 或 `needs_review` |
| C-033 | 同一原词多个项目级译名 | 进入 C 档阻塞，不自动覆盖 |
| C-034 | 用户修改决策文件 | 系统验证结构和哈希，重新计算受影响章节 |
| C-035 | 决策文件含直接状态字段 | 拒绝该字段或忽略，不允许伪造 `passed` |

### 2.5 改写、事件对照和硬门槛

| ID | 场景 | 预期 |
|---|---|---|
| C-040 | 正常章节改写 | 生成纯 `output.md`，不含内部元数据 |
| C-041 | 每个事件都有正文段落证据 | 事件级对照为 `pass` |
| C-042 | 事件缺失 | 事件对照 `fail`，状态 `rework` |
| C-043 | 事件顺序改变 | 事件对照 `fail` 或剧情级变更阻塞，不能自动通过 |
| C-044 | 事件结果改变 | 进入剧情级变更决策，未批准不能通过 |
| C-045 | 文化功能被机械删除 | 事件/功能对照失败或进入 C 档 |
| C-046 | 只改变名称、语域、表达 | 允许通过，前提是事件功能和证据完整 |
| C-047 | 正文篇幅 80%~120% | 不产生事实通过结论；只记录正常比例 |
| C-048 | 正文篇幅异常 | 产生 warning，并要求检查漏写/加戏；不能只靠比例决定 pass/fail |
| C-049 | 必须替换元素残留 | 硬门槛失败，进入 `rework` 或用户决策 |
| C-050 | 用户明确批准保留元素 | 该残留被决策覆盖，不得误报为失败，但决策必须可追溯 |

### 2.6 manifest、指纹和状态

| ID | 场景 | 预期 |
|---|---|---|
| C-060 | 基础硬门槛通过且无阻塞 | 状态可进入 `passed` |
| C-061 | 启用盲审且盲审通过 | 状态可进入 `passed` |
| C-062 | 启用盲审但未运行 | 状态保持 `awaiting_review`，不能合并 |
| C-063 | 盲审结论为返工 | 状态 `rework`，不能被视为已审通过 |
| C-064 | `passed` 仍有 blocker | manifest 校验失败或自动降级 |
| C-065 | 用户手改 manifest 为 `passed` | 哈希/审计验证失败，状态 `needs_review`，禁止合并 |
| C-066 | output 哈希变化 | 状态回退 `needs_review` 或 `ready_for_rewrite` |
| C-067 | events/decision/rules 哈希变化 | 旧正文检查失效，自动回退待重跑 |
| C-068 | 纯审计备注变化 | 不触发正文重跑 |
| C-069 | 无关章节决策变化 | 不影响本章节指纹 |
| C-070 | manifest 原子写入中途失败 | 保留旧 manifest，不产生半更新 JSON |
| C-071 | 两个进程同时更新 manifest | 互斥；一个成功，另一个失败或重试，不得静默覆盖 |
| C-072 | 运行时异常 | 状态 `error`，写入审计；人工确认后转 `needs_review`，重新校验通过后转 `ready_for_rewrite` 或暂停前安全状态 |
| C-073 | `paused` 章节恢复 | 恢复到暂停前状态；若输入指纹已变化则转 `needs_review`，不得直接继续旧正文 |
| C-074 | `needs_review` 恢复 | 指纹/文件/审计校验通过后回到安全的 `ready_for_rewrite` 或暂停前状态；仍失败则保持 `needs_review` 或转 `rework` |

### 2.7 合并和交付

| ID | 场景 | 预期 |
|---|---|---|
| C-080 | 只有 `passed` 章节 | 按 ordinal 合并到 `output/localized.md` |
| C-081 | 存在 `rework`/`awaiting_decision`/`awaiting_review`/`needs_review` 章节，或检查结果为 `blocked` | 正式合并拒绝或输出不完整报告，不得静默跳过；`blocked` 检查结果不能伪装成章节状态 |
| C-082 | 章节文件名带“已完成”但 manifest 未通过 | 不合并 |
| C-083 | `output.md` 混入计划/检查/映射说明 | 合并前纯度检查失败 |
| C-084 | 章节序号缺口 | 合并失败并列出缺口 |
| C-085 | 合并过程中某章节哈希变化 | 整次合并失败，旧正式输出保留 |
| C-086 | 合并成功 | 写入合并 revision、章节 ID、manifest 指纹到 audit |
| C-087 | 带风险版 | 只能写入独立实验路径，不能覆盖正式输出；manifest 记录 `experimental_output` 路径及 `experimental_risk` |

## 3. 故意失败测试

这些测试不是“异常日志看看就算”，而是必须断言最终状态和交付结果。

| ID | 注入缺陷 | 必须结果 |
|---|---|---|
| F-001 | 在 output 前插入 `## 写前计划` | 正文纯度失败，正式合并拒绝 |
| F-002 | 在 output 中加入 `## 本批爽点对照` | 正文纯度失败，正式合并拒绝 |
| F-003 | checks 写“盲审结论: 返工” | 章节为 `rework`，不得视为已审通过 |
| F-004 | 原文中“第二天”与“四天” | 不得直接报确定数量矛盾；疑似时保留人工核标记 |
| F-005 | 正常中文“你管我呢？” | 不得按日式句尾直接失败 |
| F-006 | 源稿同一旅馆出现三十万/三千金币 | 章节阻塞，生成矛盾决策项，不得自动选择 |
| F-007 | 手工把 manifest 状态改为 `passed` | 指纹/审计不一致，降级 `needs_review` |
| F-008 | 删除 events.json | 章节阻塞，不得改写或合并 |
| F-009 | 删除 output.md | 章节不能为 `passed`，合并拒绝 |
| F-010 | 修改 project-decisions.json 中核心译名 | 受影响章节指纹失效，回退待重跑 |
| F-011 | 只修改 audit 备注 | 正文不失效，状态保持不变 |
| F-012 | 把原始批文件复制进输出候选目录 | 合并只按 manifest 和合法路径选择，不合并原文 |
| F-013 | 分类副文件混入输入扫描目录 | 识别为非章节产物，不能增加章节数量或字数 |
| F-014 | 事件证据只写“见正文”无段落 ID | 事件对照阻塞或失败 |
| F-015 | 文化适配删除承担因果功能的元素 | 进入 C 档或事件对照失败，不得自动通过 |
| F-016 | 未加载平台规则包却声称平台审核通过 | 交付报告失败或明确标记未执行 |
| F-017 | 用户决策文件直接写 `state: passed` | 字段被拒绝/忽略，系统状态不变 |
| F-018 | 合并时某章节 output 哈希变化 | 整体合并失败，旧正式输出保留 |
| F-019 | 盲审启用但结果为 `fail` 或 `not_run` | schema/状态机拒绝 `passed`，章节保持 `awaiting_review` 或 `rework` |
| F-020 | manifest 标记 `passed` 但决策仍开放 | schema/状态机拒绝通过并降级 |

## 4. 人工验收：小型测试小说

### 4.1 测试材料最低要求

使用一部短篇或 3~5 章测试小说，至少包含：

- 一个明确的核心角色译名；
- 一个现实日本生活元素；
- 一个承担剧情功能的文化元素；
- 一个非日本来源的西幻或架空设定；
- 一个时间或数字差异；
- 一个潜在人物关系变化；
- 一个不需要剧情变更的普通章节；
- 一个需要用户决策的高风险节点。

### 4.2 人工检查表

| ID | 检查问题 | 通过标准 |
|---|---|---|
| H-001 | 用户是否清楚哪些事项必须确认？ | A/C 档问题能定位到章节和原因，不要求逐词确认 |
| H-002 | 三级本地化是否合理？ | 现实日本外壳被处理；功能元素未机械删除；西幻设定未被误改 |
| H-003 | 事件图是否能读懂？ | 事件、参与者、因果和结果与原文可核对 |
| H-004 | 事件级证据是否有用？ | 每个事件能定位到正文段落，不能只看到泛化关键词 |
| H-005 | 源稿矛盾是否被正确阻塞？ | 用户未决前不能通过；决策后只影响相关章节 |
| H-006 | 正文是否干净？ | 只有标题和正文，无计划、质检、映射或状态字段 |
| H-007 | 用户修订核心译名后是否安全重跑？ | 受影响章节自动失效，旧正文不再合并 |
| H-008 | 用户是否能恢复中断？ | manifest 和 audit 能说明当前状态、原因和下一步 |
| H-009 | 正式输出是否安全？ | 只含已通过章节，顺序正确，没有静默缺章 |
| H-010 | 未启用增强层时是否诚实？ | 报告明确“未使用参考资产/盲审/平台规则包”，不虚报质量保证 |

## 5. P0 缺陷判定

以下任一问题都属于 P0，未解释和未修复时不得进入 beta：

- 未通过、阻塞或带风险章节进入正式输出；
- 用户决策被绕过或被系统静默覆盖；
- 事件缺失、结果变化或因果变化未被阻塞；
- manifest、正文、决策或 checks 不一致仍被合并；
- 无法恢复或重跑导致旧正文继续交付；
- 正文泄漏内部计划、质检、状态或审计；
- 未执行平台规则却声称平台审核通过；
- 源稿确定矛盾被自动改写或直接带入而没有决策记录。

## 6. Beta 前报告

进入 beta 前必须提交：

1. 自动契约测试结果；
2. 故意失败测试结果；
3. 小型测试小说人工验收记录；
4. 已知缺陷清单及 P0/P1/P2 分级；
5. 未启用的 Enhance/Optional 功能清单；
6. 一次完整合并的 manifest 和 audit 指纹。
