# 技能优化

一个入口，把「结构事实 → 瘦身候选 → 审核」锁成固定顺序。原则：触发得少、判断得准、改得少、容易撤销。
优先级固定：正确性 > 行为稳定 > 架构边界 > 可维护性 > 复杂度 > 代码量。代码变少本身不是成就。

## 1. 先判适用

按**当前任务的复杂度**判断，不按仓库总代码量判断。

- 进入：第 1 段描述里的那些情形，或用户明确要求结构优化/代码瘦身。
- 跳过：改文案、颜色或简单 UI；单个明确函数的小修复；小脚本、Demo、PoC、高速原型期；简单配置。跳过时只输出一句理由，**不建图、不扫全仓、不出候选**。
- 修 Bug 时不续接全仓优化；优化与原始缺陷修复是两个独立阶段。
- 被显式点名调用也要先做适用性判断，不承诺一定产出候选。允许零候选。

## 2. 固定顺序（不可颠倒）

```
适用性判断 → Graphify-Jev → Ponytail Audit → Reviewer
（有批准项且用户已授权修改时）执行批准项 → 项目现有测试 → Graphify-Jev 复检
```

卡在哪就停在哪，并说明原因：Jev 不可用、建图失败、图过期或语言不支持 → **停止自动链路**，不得让 Ponytail 抢跑，也不得用手工搜索冒充「Jev 这步已完成」。手工搜索可以作为补充取证，但必须标明它不替代结构事实。

## 3. 目标与两种范围

开工前先确认目标项目根；只处理指定目标，绝不默认扫描整个技能柜或相邻项目。

两类范围必须分开：

| 范围 | 内容 |
|---|---|
| 候选扫描 | 自有源码。排除 `node_modules/`、`vendor/`、`dist/`、`build/`、`target/`、`cache/`、`generated/`、第三方源码、编译产物、迁移快照、lock 文件、大型静态资源，并叠加项目自定义 ignore |
| 引用取证 | `tests`、fixtures、配置、宿主契约、CLI/插件注册、字符串路由、动态调用与 DI —— **必须查**，即使它们不在候选扫描范围内 |

被排除或工具不支持的部分形成盲区，逐条记录。「没搜到」永远不等于「没有引用」。第三方与生成代码不产生瘦身候选，必要时只读其契约；无法完整验证就把相关候选降到 REVIEW。

## 4. 结构事实（Graphify-Jev）

命令形态、基线与复检约定、指标口径和外呼约束见 [references/graphify.md](references/graphify.md)。三条不可省：

1. 只复用既有能力，不重写解析、建图、遍历、循环检测或诊断引擎，不改上游来迁就接入。
2. Before/After 必须同工具版本、同扫描范围、同配置；产物写进目标项目的 `.lemon/skill-optimization/<轮次>/`，不覆盖用户已有图产物。
3. 工具没给的指标写 `UNVERIFIED` 或「不适用」并说明依据；抽样检查面（`top_n`）不得写成全仓审查完成。

## 5. 候选（Ponytail Audit）

按 [references/ponytail-audit.md](references/ponytail-audit.md)（上游原文，固定提交，未改写）生成候选。**这一阶段禁止修改任何代码。**

六类：`delete`、`reuse`、`stdlib`、`native`、`yagni`、`shrink`。

每条候选写成一个简短 Markdown 条目（字段见 [references/reviewer.md](references/reviewer.md)）。不做评分系统、不做候选数据库、不发明新的配置格式。

## 6. 审核（Reviewer）

按 [references/reviewer.md](references/reviewer.md) 逐条独立审核：只审已有候选，不另寻优化点，不照搬候选的排序与结论。结果只有 APPROVE / REVIEW / REJECT。

硬规则，任何情况都适用：

- **APPROVE 只是技术资格，不扩大用户授权。** 用户只要求审计时，只输出建议，不改代码。
- 单实现或单调用方**不是**删除理由。默认保护：Repository、Provider、Adapter、Domain interface、API/persistence/security boundary、compatibility layer、plugin/public SDK interface。
- 错误处理、fallback、入参校验、权限、安全、兼容、事务、数据恢复逻辑，不按普通瘦身删除。
- 涉及 public API、database schema、config format、CLI 契约、serialization，或动态引用无法排除、缺可靠回归测试 → 不自动执行。
- 名称、外观或参数相似，单独都不构成重复证据。

## 7. 执行、复检与停止

执行前：检查 git 状态、当前分支与用户未提交改动；保存本轮基线快照与拟议 diff。多项或跨模块改动先在目标仓库另开分支或 worktree 再做，与用户已有改动重叠的候选一律降到 REVIEW；开不出隔离分支或 worktree（含目标不是 git 仓库）时只输出建议，不改代码。目标不是 git 仓库、或拿不出可验证的回滚方案 → 只输出建议，不改代码。不 reset、不 clean、不强制 stash、不替用户提交。

预算：每轮默认最多 3 项，确有必要最多 5 项。少于上限不用凑数；不顺手重构；执行完不自行开下一轮。

执行后：跑项目**现成**的测试，以及它本来就有的 lint / type check / build（没有就记「不适用」，不为优化强装新框架）。基线本来就红或跑不起来时，先报告并降低执行权限，不把失败当绿灯。 「源码与运行结果不符」不等于缓存污染，也不设「每次测试前先清缓存」这道固定动作。出现不符时先核对三件证据：用的是哪个解释器、实际加载的是哪个文件、字节码或构建缓存处于什么状态。确认是缓存导致读数失真后，才在隔离副本或新缓存目录下重跑验证：只处理本轮由自己触发产生、且可再生成的缓存，动手前按扩展名点名确认，无法确认就不动并记 `UNVERIFIED`。用户的或共享的缓存目录一律不清理。

再以同一 Jev 版本、同一范围、同一配置复检，比较：循环依赖、跨模块影响面、职责集中、重复实现、直接依赖数量、接口与行为。

立即停止的条件：测试失败、结构恶化、接口或行为改变、证据缺失、建图失败。停止时只撤销**本轮自有变更**，按文件点名撤销，绝不覆盖用户改动。

只有 LOC 下降不构成成功。重复与依赖减少是结构收益。允许结论「无需进一步优化」。

## 8. 报告只写这些

1. 这次值不值得优化（一句结论 + 依据）。
2. 主要结构发现（来自 Jev，标明口径）。
3. 候选总数与 APPROVE / REVIEW / REJECT 各几条，各一条理由。
4. 实际执行了哪几项。
5. Before/After 对照（不可比、未运行、无法确认分别单列）。
6. 检查状态：通过 / 真失败 / 环境阻塞 / 未验证，四项分开写。
7. 是否建议下一轮，以及凭什么。
8. 回滚方式。
