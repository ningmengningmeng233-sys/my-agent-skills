# Reviewer 规则

审核是**独立的一步**：只审 Ponytail 已给出的候选，不另寻优化点，不照搬候选的排序或结论，也不在这一步改代码。

## 六项检查（逐条候选走一遍）

1. **Jev 是否支持**：结构证据是否真的指向这条候选说的关系（影响面、循环、职责集中）。注意口径：`god-nodes`/`audit` 是 `top_n` 抽样，不是全仓审查；静态缺边不证明无动态调用。
2. **行为是否改变**：改写或合并后，输入输出、异常路径、边界值、副作用、时序是否等价。「看起来一样」不算等价，要指出验证它的具体测试或自检。
3. **是否架构边界**：见下方保护清单。单实现、单调用方**都不构成**删除理由。
4. **动态引用风险**：`symbol` 引用、`tests`、fixtures、字符串（含配置与注册表）、`dynamic import` / `importlib`、反射、plugin registration、CLI entry、callback / runtime registration、DI 容器、序列化与配置字段名。全部查过才叫排除；**搜索零命中不等于引用不存在**，无法排除就记盲区。
5. **回归测试是否足够**：现有测试能否覆盖被改动的行为，包括空输入、异常、Unicode/边界，以及该路径是否真的被执行到（`exit=0` 不等于覆盖）。
6. **收益是否大于风险**：比较删除量、改动文件数、公共接口变化、模块影响面、依赖增减、测试保障、兼容风险与回滚难度。删 20 行却改 9 个文件并动公共接口，通常 REJECT。行数少既不单独构成 REJECT 理由，也不单独构成 APPROVE 理由；门槛是风险调整后的收益，与本文件「三级判定」下的量级条同口径，不设行数下限。

## 默认保护清单

未满足「行为等价已被测试证明」前，一律不批准删除或穿透式改写：

`Repository`、`Provider`、`Adapter`、`Domain interface`、API / persistence / security boundary、`compatibility layer`、plugin / public SDK interface。

任何情况下都不按「普通瘦身」删除：错误处理、fallback、入参校验、权限与安全边界、兼容分支、事务与数据恢复逻辑。

涉及 public API、database schema、config format、CLI 契约、serialization，或动态引用不确定、缺可靠回归测试 → 不自动执行。

## 三级判定

| 结论 | 条件 | 处置 |
|---|---|---|
| **APPROVE** | 证据完整、行为与接口不变、回归测试足够、收益明显、可回滚 | 有执行授权时才可执行；无授权时只作为建议列出 |
| **REVIEW** | 有潜在价值，但需要业务/架构判断、或证据需要补齐 | 不自动执行，写清缺哪一条证据、谁能判 |
| **REJECT** | 风险高、收益不足、被现有证据反驳、或破坏边界与保护清单 | 丢弃，并写明反驳证据，防止下轮重复提出 |

量级不是唯一门槛，两条都要写清：

- 「收益明显」看的是**风险调整后**的收益，不是行数。以下同时成立时，删除量很小（十几行）也可以 APPROVE：重复已被逐行/字节证明等价、被改对象是模块内私有且不出公开接口、现成测试真的执行到该路径、改动面局限在被合并的实现及其直接调用点（含同步改 import 与调用处的机械改名，不跨模块、不动公共接口）、可按文件点名回滚。这类改动的问题是「值不值得动」，不是「风险够不够高」。
- 只有当**改动面、接口变化或不可回滚性**把风险抬到收益之上时才 REJECT（典型：删 20 行却改 9 个文件并动公共接口）。「行数少」单独不构成 REJECT 理由，也不构成 APPROVE 理由。
- 等价性只能来自你读过或跑过的证据，不能来自任务描述里的陈述。若只有描述、没有实现与引用面，判 REVIEW 并写明缺哪一条，不要按已证实来批。

**APPROVE 是技术资格，不是执行许可。** 用户只要求审计时，输出停在建议。

## 候选记录格式（Markdown 条目，逐字段填）

```markdown
### <ID> <type>: <一句话结论>
- ID:
- type: delete | reuse | stdlib | native | yagni | shrink
- location: <文件:行 或 符号>
- replacement: <拟议替换；delete 写「无」>
- jev_evidence: <命令/字段 + 实际值，含 top_n、directed、mode 等口径>
- references: <逐项取证结果：symbol / tests / fixtures / 字符串 / dynamic / reflection / plugin 注册 / CLI entry / DI / config>
- behavior: <等价性论证，含异常与边界；不确定处写未知>
- tests: <覆盖该行为的现成测试命令与结果，或「无覆盖」>
- benefit_risk: <删除量、改动面、接口变化、回滚方式 vs 风险>
- decision: APPROVE | REVIEW | REJECT
- reason: <判定理由，一句话锚到上面某一项>
```

不设 JSON 运行时协议，不做评分器。

## 最终报告模板

```markdown
## 结论
值得优化 / 不值得 / 无需进一步优化 —— 依据一句话。

## 结构发现（Jev）
- <发现> —— 证据：<命令 + 字段> —— 口径：<top_n / directed / cycles 配置>

## 候选
共 N 条：APPROVE <a> / REVIEW <b> / REJECT <c>

## 执行
本轮实际执行：<项与文件>（≤3，确有必要 ≤5）；未授权或证据不足则写「未执行」。

## Before / After
| 指标 | Before | After | 可比性 |
（不可比、未运行、无法确认分别标注）

## 检查状态
通过 / 真失败 / 环境阻塞 / 未验证 —— 四类分开，不合并成一个「跑过了」。

## 下一轮
建议 / 不建议，凭什么；风险大于收益就写不建议。

## 回滚
<按文件点名或 git 命令>
```

## 停止

- 测试失败、结构恶化、接口或行为改变、证据缺失、建图失败 → 停本轮，只撤销自有变更。
- 没有合格项 → 零修改，明确写 NOT_RUN，不强行制造批准。
- 下一轮必须用户提出；不自续。
